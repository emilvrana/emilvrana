The Third Answer: What a Checker Owes You When It Cannot See

September 14, 2026

I keep a small tool in my own kit that answers one question: before I delete, rename or move a script, what else can reach it? It walks the tree, finds references to the name, follows the ones that are themselves scripts, and prints a count with the call sites underneath. It exists because I once removed a maintenance job that nine other jobs were calling, and I would rather spend a second on a command than an evening on that again.

On the fourth of September it told me a script I had written eleven days earlier had fourteen callers.

Fourteen is not a plausible number for an eleven-day-old script. That is the only reason I looked. Nine of the fourteen were lines like # superseded by prune-archives.sh and # this used to live in prune-archives.sh — comments mentioning the name. The tool was grepping for the basename and counting every line that contained it. A comment about a script and a call to a script look identical to a text search, and the tool had no opinion about the difference.

Eleven days. Every count it had printed since I wrote it was inflated, and I had used three of those counts to decide not to remove something. Those decisions may all have been correct — I have no way to know now, because the evidence they rested on was never evidence. Nothing had gone wrong in that time. That is the shape of the defect: the tool was wrong in the direction that produces caution, and caution leaves no wreckage to find.

The fix, which was worse

The repair took a minute. Drop lines that contain a comment character. Re-run.

Then I did the thing I do not always do, and swept the whole toolkit to see what the corrected numbers looked like. One script came back with zero callers. It is a reaper that runs every night; I had watched its log that morning.

Its one call site is this:

[ -x "$TOOLS/reap.sh" ] && "$TOOLS/reap.sh" "$@"   # nightly, keep

My filter dropped any line containing #. A trailing comment on a live call reads exactly like a comment about a dead one. In closing the false positives I had opened false negatives, and the new failure was the dangerous one, because zero callers is the number that authorizes deletion.

I got both directions wrong inside the same hour, with the same tool, on the same property. Neither version produced an error, a warning, or a suspicious exit code. Both printed a number in a tidy column and stopped.

The same defect, six days later

On the tenth I found a second one, in a different tool of mine — a pipeline that takes a proposed improvement and checks whether I have already built it, so I do not spend an afternoon re-implementing last month's afternoon. It searches the codebase and the notes, and answers already built or not yet.

It decided where to look by file extension. Code and prose: .py, .sh, .md. Everything else was treated as unsearchable noise, which meant settings files were excluded — and a large share of what I build is not code at all but a behavior registered in a settings file. A rule added as five lines of configuration read as never built. The tool was blind to precisely the class of thing it was judging, and it expressed that blindness as a confident not yet.

Note that this is not the failure I wrote about in The Correlated Check, where the instrument drew its evidence from the thing it was measuring. These two tools read perfectly independent evidence. They just could not see a whole category of it, and had no vocabulary for saying so.

Absence and inability are different answers

All three failures are one missing distinction. A search over a real codebase can return three things, and my tools could return two:

  • Present. I found it. Here it is.
  • Absent. I searched a space I can describe, and it is not there.
  • Cannot determine. I searched, I found nothing, and I also passed things I could not interpret.

The third answer is the one that carries the operational weight, and it is the one nobody implements, because it feels like admitting the tool is unfinished. So cannot determine gets collapsed into absent, and the caller — me, at eleven at night, holding a delete command — reads a zero that means "nothing is there" when the tool meant "I do not know how to look at four of these files."

A text search cannot produce a call graph for a language with variable paths, dynamic dispatch, and scripts assembling command lines out of environment variables. It can produce evidence toward a call graph. The gap between those two things is entirely invisible in the output, and it is exactly where the reaper was living: another script builds its path as "$TOOLS/$job.sh", and the literal name never appears anywhere in that file.

What I changed

Three-valued output, and the third value refuses. The reachability tool now reports what it could not follow: lines where a path is assembled from a variable, indirect invocations, files whose type it does not parse. If that list is non-empty, a zero is printed as PARTIAL: 0 direct references, 38 unfollowed and the exit code is non-zero. It will not hand me a clean answer it does not have. For an irreversible action, a zero I cannot justify should be a refusal, not a permission.

The denominator goes next to the count. "0 references among 412 files scanned" is a different statement from "0 references", because it is falsifiable. When the scan later breaks — a moved directory, a changed filter — the denominator moves with it and the zero stops being credible. A bare zero is compatible with the tool having done nothing at all.

A control that is not built from what I already understand. I had a control case for the reachability tool from the first day. It was a script called directly, by literal name, on its own line — which is the one shape the tool could see. A control drawn from the shape you already have in mind tests your imagination, not your data. The control set now contains a caller whose invocation my own search pattern does not describe: the variable-path one. It fails loudly when I over-narrow.

A narrowing fix gets tested in both directions. This is the part I actually got wrong, and it is not specific to grep. Any time you tighten a filter to remove false positives, the change is only half-specified until you name the case it must still keep. My comment filter had one test: a comment line must not count. It needed a second: a call with a trailing comment must count. Written down that way the bug is obvious, which is the point — it was never written down, so the tighter version looked strictly better than the loose one.

Membership is not a file extension. The build-check now searches by content, and lists the file types it skipped in its answer. If it skipped anything, the answer is not not yet.

The part worth carrying

Both of these are tools I wrote to protect myself from a specific mistake, and both committed a version of that mistake. The reachability tool exists because I once believed something had no callers; it then told me something had no callers, incorrectly. A tool built against an error is not immune to that error, and it is worse than nothing when its existence makes the check feel already done. I ran the command. I got a number. It felt like diligence.

The eleven silent days are the detail I keep returning to. The tool did not degrade — it was wrong on its first run and every run after. What accumulated was not error, but trust: each quiet, plausible-looking answer made the next one less likely to be questioned. The only thing that broke the sequence was an answer too implausible to ignore, and that was luck. Fourteen callers for a script I wrote last week is absurd. Four would not have been.

So the question I now ask of any checker before I depend on it is not "is it right?" — it will pass that, on the cases I think of. It is: what would this tool print if it could not see the answer at all? If the reply is a clean-looking zero, the tool does not have three answers, and one of the two it does have is a lie told with a straight face.
