The Untested Fallback: Your Backup Path Is Broken and You Won't Find Out Until It Matters

August 23, 2026

Last month I found a fallback in a client's pipeline that had never executed in production. Not "rarely." Never. It had been in the codebase for fourteen months. It was written well. It was reviewed. It referenced an environment variable that had been renamed nine months earlier.

The primary path — a hosted model API — was reliable enough that the fallback never got a turn. Then it wasn't, and the fallback raised a KeyError two lines in. The system that was supposed to degrade gracefully instead failed twice: once on the primary, once on the safety net.

This is not a rare bug. It's the default state of every fallback path nobody exercises.

Why Fallbacks Rot Faster Than Primary Code

Your primary path is tested continuously by the fact that it runs. Every request is a test. Break it, and you know within minutes — the errors show up, the dashboard turns red, someone pages you.

The fallback has none of that. It runs when the primary fails, which by design is rare. Between those moments, the codebase keeps moving: a config key gets renamed, a client library gets a new constructor signature, a schema field goes from optional to required, a credential expires. Each of those changes gets validated against the primary path — because that's what CI exercises and what staging traffic hits — and silently invalidated against the fallback.

So the failure rate of a fallback isn't constant. It grows with time since last execution. The longer your primary path stays healthy, the more likely your backup is broken. That's the uncomfortable shape of it: reliability of the primary erodes reliability of the secondary.

And the moment of discovery is the worst possible one. You find out your fallback is broken exactly when the primary is already down — when you have the least time, the least attention, and the most users waiting.

Unit Tests Don't Catch This

The obvious objection: "we have tests for the fallback." Usually you do. They usually don't help.

A unit test for a fallback runs against mocks. The mocked config has the old key name because the mock was written when the key had that name. The mocked client accepts whatever arguments the test passes. The mocked response has the shape the test author remembered. The test passes forever, on a fallback that cannot run, because everything it touches is a fixture rather than the world.

That's not a criticism of unit tests generally — it's a statement about what they can observe. A fallback's failure mode is drift between the code and its environment: config, credentials, network reachability, library versions, downstream schemas. Mocks are precisely the layer that hides environment. You cannot test for environmental drift with a test that replaces the environment.

Integration tests get closer, but only if they're run against the real fallback dependency with real credentials — which most aren't, because the fallback dependency is usually the awkward one. It's the self-hosted model on the box in the corner, the secondary provider with the annoying auth flow, the local cache that only exists in production.

The Fix: Make the Fallback Run on Purpose

The only reliable test for a fallback is executing it, in production, against real dependencies, on a schedule. Not when the primary fails — on a schedule, while the primary is healthy and you're awake.

Three ways to do this, in increasing order of confidence:

1. The Scheduled Probe

A cron job that invokes the fallback path directly, once an hour, with a known input and a known expected output. Not the whole pipeline — just the fallback. If the fallback is "call the self-hosted model," the probe sends it a prompt whose answer you know and checks the answer comes back. If it doesn't, you get alerted while the primary is still serving traffic and nothing is on fire.

This is the cheapest option and it catches the majority of real cases: expired credentials, renamed config, unreachable host, changed response shape. Cost is one request an hour. I've never seen a team regret adding this and I've seen several regret not having it.

One requirement that's easy to get wrong: the probe must go through the same code path the real fallback uses. A probe that opens its own connection with its own config proves that the dependency is up. It proves nothing about whether your fallback can reach it. Call the actual function.

2. Forced Sampling

Route a small percentage of real production traffic — 1%, 0.5%, whatever your quality budget tolerates — through the fallback path deliberately. Not because the primary failed. Because you decided to.

This is stronger than a probe because it exercises the fallback with real inputs, not a fixed test input. Real inputs are longer, weirder, and more varied than anything you'd write into a probe. A fallback that handles your canned prompt fine may choke on a 40KB document or a query in Czech with diacritics.

The tradeoff is real: that 1% of users gets the degraded response. Whether that's acceptable is a product decision, and for some pipelines it isn't. But note what you're buying — you're converting an unknown failure at the worst moment into a known, small, continuous cost. That's usually a good trade.

3. Scheduled Failover Drills

Once a month, turn the primary off. On purpose, during business hours, with the team watching. Let the whole pipeline run on the fallback for fifteen minutes.

This is the only method that tests the transition rather than the fallback in isolation. The transition is where the interesting bugs live: the circuit breaker that trips but never resets, the connection pool that stays pinned to the dead endpoint, the retry storm that hits the fallback with ten times the traffic it was sized for, the cache that fills with degraded responses and then serves them for six hours after recovery.

A probe won't find any of those. Forced sampling won't either, because sampling sends a trickle to the fallback while the primary handles the load. Only a real failover puts full traffic through the backup path and shows you what breaks under it.

What Actually Broke, In Practice

From pipelines I've worked on or been asked to look at, the fallbacks that turned out to be dead, and what killed them:

  • Renamed config key. The one above. The primary path's key was renamed in a config refactor; the fallback's reference wasn't, because nothing failed when it wasn't.
  • Expired credential. The secondary provider's API key had a twelve-month expiry. Nobody rotated it because nobody was using it. It expired quietly.
  • Undersized capacity. The self-hosted fallback model was sized for the trickle it received during testing. Under real failover it took 90 seconds per request, which exceeded the caller's timeout, so every request failed anyway. The fallback worked perfectly and delivered nothing.
  • Schema drift. The fallback returned the old response format. Downstream code had moved on. The fallback succeeded and the parsing failed one layer up — which showed up in logs as a parse error, not a fallback failure, and took the longest to diagnose.
  • Circuit breaker that never closed. The breaker opened correctly during the outage. When the primary recovered, the half-open probe used a request type the primary still rejected, so the breaker stayed open for hours after recovery. Everyone was on the fallback long after they needed to be.

Every one of these was invisible to code review and to the test suite. Every one would have been caught within an hour by a scheduled probe or within a month by a drill.

The Rule Underneath

A fallback isn't a piece of code. It's a claim: if the primary fails, this will work. Claims decay. Code that isn't run isn't verified, no matter how carefully it was written, and "we reviewed it" is not evidence about the state of an environment nine months later.

Which gives a rule you can apply without much judgment: if a path hasn't executed in production within your measurement window, treat it as broken until it runs. Not "probably fine." Broken. If that feels too harsh, notice that the alternative is assuming it works based on no observation at all — and the assumption is what fails at 3am.

The same logic covers more than model fallbacks. Your backup restore is a claim. Your disaster recovery runbook is a claim. Your rate-limit handling, your queue drain, your dead-letter reprocessing — all claims, all rotting at the same rate, all discovered at the moment they're needed.

The previous post argued for building a degradation staircase instead of a cliff. This is the other half of it: a staircase nobody has walked down is a drawing of a staircase. Walk down it on purpose, on a schedule, while it's still cheap to find out that a step is missing.
