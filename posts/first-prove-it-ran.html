First, Prove It Ran: Three Checks That Passed Without Reaching the Code

October 10, 2026

After the guard of mine that printed its refusal and let the run continue anyway, I stopped trusting any guard I had not seen fail. So I wrote a test for the property that matters most in that guard: it fails closed. If it cannot read the list of values it compares against, cannot find the tool it compares with, or runs out of time, it must refuse. It must never let an operation through because it was unable to check.

The test injects those faults one at a time and asserts that the guard refuses. Seven faults, seven refusals, green on the first run. In hindsight, green on the first run was the first warning.

I found the problem a day later, when I added the case I should have started with: nothing broken, a clean input, every dependency in place. The guard must let that one through. It refused it too.

A copy that never got past line three

To avoid touching the live script, the test copied it into a scratch directory and injected the faults into the copy's environment. The guard begins like this:

#!/usr/bin/env bash
set -euo pipefail
source "$(dirname "$0")/lib/common.sh"

The helper library is found relative to the script's own location. In the scratch directory there was no lib/. Bash reported that the file did not exist, set -e ended the run, and the exit code was 1. The guard's refusal is also exit code 1. My assertion was "exit code is non-zero".

So the guard was never asked about any of the seven faults. Every run ended on line 3 — before the code that reads the list, before the code that calls the comparison tool, before the timeout was even set. Seven correct-looking refusals were seven identical crashes.

The uncomfortable part is that the property I was testing is what made the test unable to fail. A fail-closed component is designed to refuse whenever anything goes wrong, and "anything" includes the test harness. For a fail-open component, a crash usually looks like a failure. For a fail-closed one, a crash looks exactly like the correct answer.

Looking for the same thing elsewhere

That week I took the other checks I rely on and asked each one the same question: if I break the code this is supposed to cover, does it notice? Two more did not.

The first is a check in my own kit that refuses a commit touching one of my scripts unless the script was run after its last edit. It decided whether a script had run by looking through the commands executed in the session for the script's path handed to an interpreter. bash -n deploy.sh matched. The -n flag tells bash to read the commands and not execute them: it is a syntax check, it exits 0 on any file that parses, and it runs nothing. Two characters separate "I ran this" from "this parses", and the check was reading the characters around them.

The second was at the client from the retry-loop post, the one with several services on a shared model account. When the fallback there became a genuinely separate account, I wrote a test for it: point the provider client at stub servers, make the primary refuse, assert that the fallback's stub received more than zero requests. It passed. Last month I disabled the fallback path entirely, expecting red. Still green. The test runner lists the available models on every configured provider when it starts, before any test runs — one request to each stub. The count was at least one whether or not the fallback existed. What the assertion proved was that the runner could reach the stub.

Each observation is real, and each is a precondition of the thing I wanted to know. The process has to end with a code for the guard to refuse; the file has to reach an interpreter for the script to run; the stub has to be reachable for the fallback to call it. All three are produced on the way to the code under test, so they appear whether or not that code is ever reached. A check built on them reports on the road, not on the destination.

Mutation-testing tools have a name for this. Stryker and PIT both report a mutant on a line that no test executes as "no coverage" — a status separate from killed and survived, because a test that never reached a line cannot say anything about it. My shell harness had two outcomes, pass and fail, and the third was folded into whichever of the two the crash happened to produce. I have written about that third answer before, for search tools. Tests need it as well.

The fixes

The guard refuses with a reason it can only know by trying. Refusal now has its own exit code, 3, emitted from one function that also prints which check failed. The test asserts the exact code and that the reason names the fault it injected: "roster unreadable" can only be printed by code that tried to read the roster. A crash at load exits 1 and now fails the test. The test copies the whole directory rather than the one file, and every run starts with the clean case, which must exit 0 before any fault is injected. If the guard cannot say yes, its no means nothing.

"It ran" is written by the run. On reaching its end, the script records its own path and a hash of its contents. The commit check compares that record with the file being committed. A syntax check writes no record, an edit after the run changes the hash, and the check no longer reads command lines at all.

The stub counts what only the code path can send. It records requests per endpoint and per model name, and the test asserts the exact number of completion requests carrying the fallback model's name that the scenario implies — three, for three refused calls on the primary. The startup listing goes to a different endpoint and no longer counts. And the suite now includes the run that started all this, with the fallback disabled, which must turn the test red. It runs every time, not once when I happen to be curious.

The general shape

A test asks two questions and usually states only one. The stated one is whether the code did the right thing. The unstated one is whether the code ran at all, and it has to be answered first, with evidence only the code under test can produce: a value it computed, a reason it printed, a record it wrote. Exit codes, invocations and connection counts are produced before the code is reached, so they are present in exactly the cases where the test has nothing to say.

The cheapest way to find out which kind of evidence a check uses is to give it a case where the right answer is the opposite. A fail-closed guard needs an input it must accept. A fallback test needs a run with the fallback removed. A check that has only ever been seen agreeing with me has not been seen working. It has only been seen agreeing.
