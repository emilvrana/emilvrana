Temporary Is a Lifetime, Not a Place: Who Ends a Temp File

October 17, 2026

The scripts around my agents write a lot of scratch files: tool outputs, partial responses, copies of things under test. Earlier this month I went into the per-user temporary directory on my Mac looking for one of them and found 340 files carrying the prefixes of my own tools. Most were harmless. Eleven were not. They were curl configuration files, each holding an authorization header. That is how my scripts keep a token off the command line, where any process listing would show it. Mode 600, as intended, and still a live credential left on disk for weeks after the run that wrote it.

Every one of those scripts sets a cleanup handler on exit. None of them had ever reported an error. Over the next week I found four mistakes around that directory. Two explain how the files got there, and two came from my own attempts to measure and clean it. They share one shape. Each time, something asked the directory a question that only a file's owner can answer.

The shell that never exits

The scripts that call an API retry on transient failures, and several of them retry by starting over:

cfg=$(mktemp -t api)
trap 'rm -f "$cfg"' EXIT
printf 'header = "Authorization: Bearer %s"\n' "$TOKEN" > "$cfg"

if ! curl --fail --silent -K "$cfg" "$URL"; then
    [ "${ATTEMPT:-1}" -lt 5 ] || exit 1
    export ATTEMPT=$(( ${ATTEMPT:-1} + 1 ))
    sleep 30
    exec "$0" "$@"          # start over with clean state
fi

I liked this because the second attempt begins with nothing left over from the first. That is also the problem. exec does not start a new process. It replaces the program running in the current one, under the same process ID, and the shell that set the trap does not exit. It simply stops existing. Bash runs an EXIT trap when the shell exits, and this shell never does:

$ bash -c 'trap "echo cleanup" EXIT; true'
cleanup
$ bash -c 'trap "echo cleanup" EXIT; exec true'
$

The new incarnation creates its own file, sets its own trap and removes its own file when it finishes. The previous file's name existed only in a variable of the program that was replaced. Every retry leaked exactly one credential file. The run reported success, because eventually it was one.

The override three forms do not read

My first fix was containment. I pointed TMPDIR for all my tools at a directory of my own, so that whatever leaked would at least leak somewhere I could count. A day later the shared directory was still growing.

On the macOS I run, mktemp has two kinds of call. A template with a path, such as mktemp "$TMPDIR/x.XXXXXX" or mktemp -p "$dir" x.XXXXXX, puts the file where the path says. The three forms without a template, mktemp, mktemp -d and mktemp -t prefix, put it in the per-user directory under /var/folders, whatever TMPDIR says. The manual states that -t uses TMPDIR if it is set. On this machine it does not:

$ export TMPDIR=/private/tmp/
$ mktemp -u -t pre                  # -u: print the name, create nothing
/var/folders/…/T/pre.soOY3KNs88
$ mktemp -u -p "$TMPDIR" pre.XXXXXX
/private/tmp//pre.6NVZ9w

The script above has this defect too: mktemp -t api. Nothing made it visible. Every call succeeded. The templated forms honoured the override, so a spot check of "does the override work" passed, and I had done one, with a templated call. The files were not escaping the policy. They were created outside it.

A directory that is not mine

To prove the leak had stopped, I wanted a number: entries in the shared directory before and after a day of ordinary work. I wrote a watchdog that measured its growth. I also added the directory to my nightly secrets scan, which looks for live token values on disk and refuses to report clean over anything it could not read.

Both failed on the first night. The per-user directory is not only mine; the system keeps its own folders there. 29 of them, owned by other users, blocked for 6 to 21 seconds on every attempt to open them and then failed with "Interrupted system call", not "Permission denied". My watchdog skipped permission errors and retried interrupted calls, because an interrupted call is normally transient. It spent its whole time budget retrying folders that would never open and timed out without a count. The scan did what a fail-closed tool should do and refused, every night. A scan that refuses every night has the coverage of no scan, with better manners.

The sweeper that judged by age

The fixes below stopped new leaks, but weeks of old files were still in my temp root and no cleanup handler was ever coming back for them. So I wrote a sweeper: delete anything in my temp root not modified for three days.

A week later I went to read the log of a small long-running worker of mine, one that logs only when something goes wrong, and the file was not there. The worker was running. lsof +L1, which lists open files whose link count has dropped to zero, showed it holding its log and its single-instance lock, both deleted. The sweeper had removed them two nights earlier.

The worker kept both under TMPDIR because I had thought of them as runtime files. A lock file is created when the daemon starts and never modified again, so once the daemon has been up for three days, "not modified for three days" is the lock's normal state. A quiet daemon's log looks the same. The sweeper treated age as evidence of abandonment, and the two files whose whole purpose is to survive a quiet stretch were the first to qualify.

Nothing reported an error. Unlinking a file that a process holds open is legal. The process goes on writing into an inode that no path names, and the disk space comes back only when the file is closed. The log was being written where nobody could read it. The lock was worse. A flock lock is held on the file, not on its name, and the file no longer had a name. The next start of the worker would have created a new file at the same path, locked it without contention and run alongside the first.

Four assumptions about one directory

"Temporary" sounds like a property of the file. It is a claim about the file's lifetime: it will be gone when nobody needs it. Every mechanism I had tied that claim to a place instead: a directory where temporary things go, a handler that runs when a shell leaves, a sweeper that tidies by age. Someone who knows nothing about what is in a place can still tidy it. A lifetime can be ended correctly only by something that knows whether the owner is still alive, and none of my four mechanisms asked.

The fixes

One run directory, created with an explicit path. Each script makes exactly one directory at start, run=$(mktemp -d "$TMPROOT/run.XXXXXX"), and creates every other file inside it by name. There is no other mktemp call. My commit check refuses any mktemp whose template has no path. That is easier to enforce than remembering which forms read which variable.

Retry in a loop, not with exec. The attempt now runs in a loop inside one shell, so the shell that set the trap is the shell that exits. The one script that genuinely needs a fresh process removes its run directory explicitly on the line before exec. I rotated the token those eleven files held before deleting them.

The sweeper asks about the owner, not the clock. Each run directory holds a file with its owner's process ID and start time. The sweeper removes a directory only when no process with that ID and that start time exists. The start time is there because process IDs are reused. Age is no longer an input at all.

Long-lived files live where nothing sweeps. Locks and daemon logs moved to a state directory that no sweeper touches. The worker also checks once a minute that its lock path still names the inode it holds, comparing stat on the path with fstat on its open descriptor, and exits loudly if they differ. A daemon that has lost its lock should stop, because the alternative is two of them.

The readers list before they open. The watchdog and the scan read the directory's top level first, which opens none of the subfolders, and check each entry with lstat, which reads its owner and mode without opening it. An entry owned by another user and not writable by mine cannot hold anything my scripts wrote, so it is not opened. It is printed by name, with a count: "29 skipped, owned by another user". That is an explicitly partial answer, the third answer from an earlier post, rather than a refusal every night.

A count that does not care how a file was made. The test suite now runs between two counts of my prefixes at the top level of the shared directory, and the difference must be zero. That count would have caught the template-less forms on the first day, because it does not depend on which call created the file. A check that inspects the calls can only find the calls I already know about.

The general shape

The lesson is narrower than "clean up after yourself". I did clean up after myself; every script had a handler. The handlers were tied to an event, the shell exiting, which I treated as the same thing as the work being over. In one of the ways a script can end, it is not. Whatever ends a temporary file's life has to answer one question: is the thing that made this file still alive? An exit handler cannot answer it if the exit never comes. A clock cannot answer it at all.
